# @memobrain/cloud-features

La UI di **gestione dei vault cloud**, scritta una volta sola per la console web, il desktop e il workbench del browser ([ADR-0037 §2](../../docs/adr/0037-registro-funzioni-e-cloud-features.md)).

## Regola

Ogni nuova funzione di gestione dei vault cloud (vault, dispositivi, utilizzo, condivisioni, grant, inviti, directory…) **nasce qui**, mai direttamente in `web/src/pages` o in `packages/workbench/src/settings`. Gli host si limitano a montare i componenti e a passare un adattatore e qualche callback. La funzione va registrata in `shared/parity/features.yaml` con i test di entrambe le superfici.

## Scelte

- **Stile.** I componenti usano quelli di `@memobrain/ui` (classi `nd-*`) e aggiungono solo classi di layout `mbcf-*`; niente stile inline né `<style>` (CSP, V-02). La console carica `@memobrain/ui/styles.css` e `@memobrain/cloud-features/styles.css`. Il workbench non può caricare il design system della console (le sue regole globali toccherebbero l'editor): importa `@memobrain/cloud-features/workbench.css`, che prende solo le regole dei componenti (`@memobrain/ui/components.css`, soltanto classi `nd-*`) e dentro `.mbcf` mappa i token `--nd-*` su quelli del workbench.
- **Testi.** Il pacchetto ha un proprio dizionario it/en (`src/i18n.ts`, interpolazione `{{nome}}` e plurali `_one`/`_other` come i18next); l'host passa solo la lingua (`lang`). Gli stessi testi valgono così su ogni host, e `i18n.test.ts` applica i controlli di coerenza di `@memobrain/ui` (`i18nCheck`).
- **Caricamento.** `@memobrain/cloud-features/panels` espone i componenti per il caricamento su richiesta, `./port` e `./flags` le parti leggere; il pacchetto è senza effetti collaterali (`sideEffects`: solo il CSS). Il workbench carica i pannelli con `lazy` (`packages/workbench/src/cloud/lazyPanels.tsx`) e li tiene fuori dal bundle iniziale.
- **Dati.** I componenti usano react-query dell'host (`QueryClientProvider`), con chiavi proprie per adattatore (`cloudKeys`); `onChanged` permette all'host di aggiornare il resto (utilizzo, collegamento del vault aperto).

## Regola delle chiamate (ESLint)

Le API che la porta copre si chiamano solo dagli adattatori (ADR-0045 §7, `eslint.config.js`): nella console niente `api.GET('/vaults')`, `/shares…`, `/me/devices`, `/me/usage`, `/me/groups`, `/shared-with-me`, `/directory/…` né `fetch('/api/v1/…')` verso di esse (l'esportazione ZIP di `VaultExport` resta ammessa: i suoi percorsi non sono della porta); in `packages/workbench/src/settings` e `sharing` niente `api.sharing.*`, `api.sync.*CloudVault*`/`devices`/`revokeDevice`/`usage`, alias della facciata o import dei moduli `wailsjs`. Si usa la porta (`useCloudPort` nella console, `CoreCloudPort` nel workbench).

## Test

Due suite dei componenti (`src/testing/suite.tsx` per i vault, `src/testing/accountSuite.tsx` per dispositivi, utilizzo, condivisioni, inviti, mount e gruppi; esportate da `@memobrain/cloud-features/testing`) girano su tre backend: `fakeCloudApi` simula la REST, il mock di Wails i binding e, sul core Go vero compilato in WebAssembly, lo stesso `fakeCloudApi` risponde al core. I semi usano UUID, come chiede il contratto (il core li decodifica).

`@memobrain/cloud-features/testing/contract` (solo Node, fuori dall'indice del pacchetto) legge `api/openapi.yaml` e con `contractFetch` avvolge un finto cloud: ogni richiesta è ricondotta a un'operazione, corpi e risposte JSON sono validati, e i problemi si raccolgono in un elenco che il test vuole vuoto. Lo usano la corsa sul core e il mock di Playwright (`web/e2e/cloudMock.ts`).

```sh
yarn workspace @memobrain/cloud-features run test                                  # RestCloudPort su un finto server REST (src/testing/fakeRest.ts, fakeCloud.ts) e il contratto
yarn workspace @memobrain/workbench exec vitest run src/cloud/CoreCloudPort.test.tsx  # CoreCloudPort sul mock di Wails
task test-core                                                                     # CoreCloudPort sul core WebAssembly in Node (CoreCloudPort.core.test.tsx), con il cloud validato sull'OpenAPI
```
