Web UI ​

La Web UI è un'applicazione React 19 + TypeScript costruita con esbuild (ADR-0025). La build di produzione (web/dist) viene copiata in services/cloud/web-embed/dist e incorporata nel binario del cloud con go:embed. Il router del cloud passa alla SPA ogni percorso che l'API non gestisce (NotFound in services/cloud/internal/httpserver/server.go, httpserver.Deps.WebUI), quindi /api/* (compreso lo stream SSE /api/v1/events) e /metrics non cambiano.

Ha tre parti:

PartePaginaPer chi
Console utenteindex.html (SPA)ogni utente autenticato: vault, dispositivi, condivisioni, spazio, account
Console adminindex.html, sotto /adminruolo admin di GET /me (ADR-0041 §1). La UI nasconde solo le voci: l'autorizzazione vera è sul server (ogni operazione con x-required-role: clarae-admin in api/openapi.yaml risponde FORBIDDEN senza il ruolo, admin() in services/cloud/internal/admin/http.go)
Workbench del vaultworkbench.html, rotta /vaults/:id/openla stessa UI del desktop (@clarae/workbench) sul core Go del desktop compilato in WebAssembly (ADR-0029, ADR-0030). Guida per gli sviluppatori: desktop-web-sync.md

Console e workbench sono due documenti HTML distinti, con bundle, foglio di stile e CSP propri: lo stile globale della UI desktop non deve toccare la console, e la console mantiene la politica più stretta. Si passa dall'una all'altro sempre con un caricamento completo della pagina.

PercorsoContenuto

Rotte del workbench (pagina workbench.html, web/src/workbench/main.tsx):

Nelle build E2E il workbench accetta anche ?local (apre una cartella del browser senza cloud) e ?fstrace (log delle chiamate al file system).

Instradamento lato server (web-embed; il dev server di web/scripts/esbuild.mjs sceglie la pagina allo stesso modo e inoltra /api/ al cloud):

  • un percorso che corrisponde a ^/vaults/[^/]+/open/?$ riceve workbench.html con la sua CSP; se la build non ha workbench.html riceve la console. Lo stesso pattern è in web/src/shared/routes.ts (usato dal dev server e dalla pagina del workbench); il test Go TestWorkbenchRouteMatchesTheWebUI controlla che i due coincidano;
  • /api e /api/* non sono mai serviti dalla SPA (404 semplice; un percorso sconosciuto sotto /api/v1 riceve dal router il 404 problem+json dell'API);
  • un file esistente nella build viene servito così com'è;
  • un percorso inesistente con estensione è un 404 (un asset sbagliato non diventa HTML);
  • ogni altro percorso riceve index.html (fallback SPA), compreso /auth/callback;
  • solo GET e HEAD; gli altri metodi rispondono 405.

Autenticazione ​

  1. All'avvio la SPA legge GET /api/v1/client-config (pubblico, ADR-0008): issuer, web_client_id (default clarae-web, variabile OIDC_WEB_CLIENT_ID) e audience. La lettura si ritenta due volte (dopo 0,3 s e 1 s); un fallimento non viene ricordato, quindi la richiesta successiva riparte (createOidcAuth in web/src/auth/oidc.ts).
  2. oidc-client-ts esegue Authorization Code + PKCE contro Keycloak con il client pubblico clarae-web; redirect su <origin>/auth/callback, scope openid profile email. Le redirect URI del realm di sviluppo (deploy/keycloak/realm-clarae.json) coprono http://localhost:5174/* e http://localhost:18081/*.
  3. Token e stato PKCE stanno solo in sessionStorage e spariscono alla chiusura della scheda.
  4. Rinnovo (web/src/auth/oidc.ts), sempre con il refresh token e mai con un iframe nascosto (la CSP lo vieterebbe):
    • automaticSilentRenew di oidc-client-ts rinnova prima della scadenza;
    • getUser() rinnova anche quando il token scade entro RENEW_MARGIN_S = 30 secondi, o è già scaduto (per esempio dopo la sospensione del portatile). I chiamanti concorrenti, compreso il core del workbench che chiede token, condividono un solo rinnovo;
    • se il rinnovo fallisce, un token ancora valido si usa finché dura; un token scaduto fa uscire l'utente localmente;
    • all'evento di token scaduto si tenta un ultimo rinnovo, poi l'utente viene rimosso e la guardia lo rimanda al login.
  5. Una risposta 401 dall'API (query o mutation) riavvia il login sul percorso corrente.
  6. Workbench: quando il core chiede un token e la sessione non si può rinnovare, la pagina scrive prima le modifiche in sospeso (flush() del workbench, al massimo 5 s) e poi va al login, una volta sola (getToken in web/src/workbench/launch.ts).
  7. Guardie (web/src/auth/guards.tsx): RequireAuth manda gli anonimi al login ricordando percorso e query; se la sessione non si può leggere o il login non parte (cloud o identity provider irraggiungibili) mostra l'errore con «Riprova» invece di restare su «Reindirizzamento…» (error e retry di AuthProvider); la pagina del workbench fa lo stesso con un pulsante che ricarica; RequireAdmin mostra "Non consentito" senza il ruolo. Il ruolo è quello di GET /me (Me.role, la riga users.role con cui il server autorizza, ADR-0041 §1), non i ruoli realm dell'access token, che dopo un cambio restano vecchi fino al rinnovo; i ruoli del token servono solo se /me non risponde (useAdminAccess in web/src/api/queries.ts). Le azioni che il server rifiuta sempre (sospendere o eliminare sé stessi) non compaiono.
  8. returnTo: viaggia nello state OIDC e al ritorno si accettano solo percorsi same-origin (che iniziano con / ma non con //), altrimenti /. Se il percorso è una rotta del workbench, /auth/callback lo carica con location.replace invece di navigare nel router della console.

Doppio di test. Con CLARAE_E2E=1 (dev server di Playwright e build E2E) main.tsx e workbench/main.tsx caricano auth/e2e.ts, che legge l'utente da sessionStorage['clarae.e2e.user'] e manda il login su /e2e-signin (intercettato dai test). import.meta.env.CLARAE_E2E è una costante di build (define di esbuild): nelle build di produzione il ramo e il modulo spariscono. Si verifica con command grep -r "clarae.e2e" web/dist, che non deve trovare nulla.

Gestione dei vault nella console ​

FunzioneDove
Elenco e ciclo di vita/vaults (web/src/pages/Vaults.tsx) monta CloudVaultsTable su un RestCloudPort: elenco (GET /vaults) con dimensione, file e data di creazione; Apri (link a /vaults/:id/open); Rinomina (PATCH); Elimina con conferma (DELETE, eliminazione logica con conservazione); sezione Vault eliminati (GET /vaults?include_deleted=true) con Ripristina (POST /vaults/{id}:restore). L'API non espone i giorni di conservazione, quindi la console non mostra la data di rimozione definitiva. Dopo ogni modifica si invalidano le query vaults e usage
Nuovo vaultun vault condiviso si crea via REST (POST /vaults con Idempotency-Key); un vault privato apre il workbench sulla rotta di creazione /vaults/new/open?kind=private&name=…, perché envelope e chiave di recupero li produce il core Go e la console non duplica la crittografia (ADR-0037 §2). Con web_workbench spento la creazione di vault privati e Apri non sono offerti
Condivisi con mesotto la tabella, MountsList (lo stesso componente di Impostazioni › Condivisione del workbench, ADR-0045 §7): le condivisioni accettate (GET /shared-with-me, letta per intero una pagina dopo l'altra), ognuna aperta come mount con /vaults/<vault_id>/open?share=<id>; nascosta se non ce ne sono. Il campo mounts di GET /vaults non viene usato: il server lo restituisce sempre vuoto
Download ZIPcolonna aggiuntiva della tabella (VaultExport.tsx). Condiviso: prima lo stream diretto GET /vaults/{id}/export.zip; se il server risponde 409 INVALID_STATE (vault troppo grande) crea un job (POST /vaults/{id}/exports) e lo interroga ogni 2 s fino al link di download (web/src/export/sharedExport.ts); un archivio servito dall'API stessa si salva con Salva ZIP…, che apre prima la scelta del file e poi lo scrive su disco in streaming con il token corrente (mai in un URL), mentre un link presigned resta un download normale. Privato: passphrase o chiave di recupero, poi key-envelopes, tree e blob cifrati dall'API, decifrati e compressi nel browser da @clarae/vaultcrypto-web (web/src/export/privateExport.ts). Apre envelope v1 e v2 (ADR-0034, crypto-design.md §5.3) e prova la passphrase normalizzata NFC prima delle forme grezze (§5.4); rifiuta parametri KDF deboli. Lo ZIP va su disco in streaming con la File System Access API, altrimenti in un Blob (avviso oltre 500 MB). Solo un blob che il server non ha più viene saltato e annotato nel resoconto; gli altri errori vengono ritentati e, se persistono, l'export si ferma senza salvare uno ZIP incompleto. Le chiavi restano in memoria al più per security.vault_lock_minutes di inattività e si azzerano alla chiusura del dialogo
Dispositivi/devices: DevicesPanel, elenco e revoca; il dispositivo di questo browser è segnato e non si revoca da qui
Spazio/usage: UsagePanel, spazio usato e quota con il livello calcolato dal server (barra con soglie) e lo spazio di ogni vault
Condivisioni/shares: InvitationsList (inviti ricevuti da accettare o rifiutare, condivisioni accettate con MountsList e apertura nel workbench, rifiutate) e SharesManager (condivisioni create o gestite: grant a utenti e gruppi con ricerca nella directory, permessi viewer/editor/manager, modifica, revoca), elenchi a pagine con «Carica altri». Il flag sharing spento nasconde gli elenchi
Account/account: i gruppi dell'utente (MyGroups, GET /me/groups); export dei dati personali (GDPR, GET /me/export, file JSON); Dimentica questo browser; eliminazione dell'account (DELETE /me, conferma con lo username e, se ci sono vault privati, presa d'atto della perdita dei dati)

Dimentica questo browser (web/src/layout/ForgetBrowser.tsx, web/src/workbench/forget.ts) cancella le copie dei vault che il workbench tiene in OPFS per l'account connesso (la sua cartella accounts/<chiave>, vedi «Dati del browser per account») e i suoi marker. Lo usano sia il pulsante della pagina Account sia Esci (Shell), che esce comunque anche se la cancellazione fallisce. Le copie di altri account dello stesso browser non vengono né elencate né toccate: restano finché quegli account non escono o non dimenticano il browser (o finché non si cancellano i dati del sito). L'eliminazione dell'account cancella le copie dell'account senza chiedere (le modifiche non caricate non si possono più caricare), chiude il motore di una sua scheda del workbench aperta e dimentica la registrazione del dispositivo, poi esce.

  • Se i marker dicono che una copia ha modifiche non caricate o conflitti, un dialogo elenca i vault e chiede conferma prima di cancellare (D-04). Una copia il cui vault cloud è stato eliminato altrove è elencata senza link («il suo vault cloud è stato eliminato»).
  • Se un workbench aperto in un'altra scheda tiene i file (NoModificationAllowedError/InvalidStateError), il risultato è busy e il dialogo offre Riprova o Chiudi quella scheda e riprova. Quest'ultima manda la richiesta leave sul BroadcastChannel clarae-workbench: la scheda scrive le modifiche, le carica (anche di un vault condiviso) e aggiorna il suo marker, blocca e cancella la copia privata se può, poi torna alla console. La console riprova ogni secondo per al massimo 30 s ma non cancella nulla finché un marker elenca modifiche non caricate che l'utente non ha già confermato: se la pagina del workbench se n'è andata (Web Lock clarae-workbench libero) quelle modifiche restano nel browser e il dialogo di conferma le elenca; se la scheda resta aperta (perché conserva modifiche) lo dice. Anche Riprova rilegge i marker prima di cancellare.

Un solo codice per console e workbench. Tutta la gestione cloud della console (vault, dispositivi, spazio, condivisioni, inviti, mount, gruppi) è fatta dai componenti di @clarae/cloud-features dietro CloudPort: le pagine di web/src/pages (Vaults, Devices, Usage, Shares e i gruppi di Account) si limitano a montarli con un RestCloudPort (useCloudPort, web/src/api/cloud.ts) e a passare i link verso il workbench. Desktop e workbench montano gli stessi componenti su CoreCloudPort, sui binding Go (packages/workbench/src/settings/AccountDevices.tsx, packages/workbench/src/sharing). ESLint vieta nella console le chiamate REST dirette ai percorsi della porta. Una funzione nuova di gestione dei vault cloud nasce quindi in @clarae/cloud-features, con un metodo di CloudPort implementato da entrambi gli adattatori, mai in web/src/pages (desktop-web-sync.md).

Host del workbench nel browser ​

Il codice sta in web/src/workbench. Il funzionamento è descritto in desktop-web-sync.md, «Host del browser»; in breve:

  • Ingresso e avvio (main.tsx, launch.ts): login OIDC, un solo workbench per browser con il Web Lock clarae-workbench e, nello stesso passo, quello della 1.4 (vedi «Profilo della 1.4 e doppio Web Lock»); gli handle sincroni di OPFS sono esclusivi, la seconda scheda mostra un messaggio, avvio del core e cancellazione delle copie private lasciate da una scheda chiusa (sweep all'avvio). Poi controllo del flag web_workbench: se è spento (ConfigAPI.Effective) la pagina lo dice, anche se l'indirizzo è stato digitato a mano. Infine apertura e collegamento del vault (OpenVault + LinkExisting, oppure OpenMount) e montaggio della UI con kind: 'web'. Le chiamate di avvio passano dal client tipizzato generato dai binding (coreClient(core, ms) di core.gen.ts, ADR-0045 §5), con un limite di tempo.
  • Worker (worker.ts, bundle autosufficiente): shim fs/path/process su OPFS (opfs-fs.ts), sqlite-wasm con il VFS opfs-sahpool, host per il core, poi il programma Go (wasm_exec.js è incluso nel bundle).
  • Bridge (bridge.ts): RPC verso il worker, window.go e window.runtime per i moduli Wails generati. Se il worker o il programma Go muore, le chiamate rifiutano con CoreDeadError e la pagina mostra un overlay fatale con Ricarica; un limite superato dà CoreTimeoutError.
  • Dati del browser per account (storage.ts, device.ts): un profilo del browser può essere usato da più account. Ogni account ha cartelle OPFS sue, accounts/<chiave>/fs (il file system del core) e accounts/<chiave>/sqlite (il pool SQLite), con la chiave derivata da origine del server e sub dell'account (SHA-256, accountKey), marker suoi e una registrazione del dispositivo sua (IndexedDB clarae-device, chiave [server, sub]). Il worker apre solo lo spazio dell'account connesso, i messaggi «lascia il workbench» della console portano l'account e le schede di altri account li ignorano; se nella stessa scheda arriva un token di un altro account, il workbench scrive le modifiche e torna alla console.
  • Profilo della 1.4 e doppio Web Lock (legacyNames.ts, migrate.ts, storage.ts, markers.ts, device.ts, forget.ts, main.tsx; ADR-0052): i nomi con cui la 1.4 teneva i dati nel browser sono in legacyNames.ts, l'unico file che li nomina (fissati da legacyNames.test.ts). Alla prima apertura del workbench di un account, sotto i Web Lock e prima che il core parta (launch.ts), migrateAccountStorage porta accounts/<chiave vecchia> ad accounts/<chiave nuova> (la chiave dell'account cambia insieme al nome; il record di un insieme adottato della 1.3 segue il suo account), migrateMarkers unisce i marker delle due chiavi (vince la voce con modifiche), scrive la nuova e toglie la vecchia solo dopo averla riletta, e device.ts copia al primo accesso le registrazioni dal database IndexedDB vecchio al nuovo e cancella il vecchio. Lo spostamento di una cartella (migrate.ts) riprende se si interrompe: FileSystemHandle.move dove c'è, altrimenti copia, confronto, marker scritto per ultimo e rimozione dell'originale; una copia interrotta si scarta e si rifà, una destinazione che non ha il marker è uno spazio con una storia sua e si tiene. Tema e lingua della console e gli strumenti recenti dei disegni si leggono dalla chiave nuova, poi dalla vecchia, e si scrivono nella nuova (la vecchia resta); l'uscita e «Dimentica questo browser» cancellano anche ciò che resta sotto i nomi vecchi. Doppio Web Lock: la pagina prende il lock clarae-workbench e quello della 1.4 (WORKBENCH_LOCKS, in ordine fisso), e parla e ascolta su entrambi i BroadcastChannel (sul canale vecchio il messaggio porta la chiave dell'account vecchia), così una scheda 1.4 rimasta aperta durante un aggiornamento e la pagina nuova non aprono mai insieme gli handle OPFS. Se la scheda vecchia tiene il lock, la pagina nuova riprova per circa due secondi e poi mostra «Un vault è già aperto in un'altra scheda di questo browser» (workbench.busy): va chiusa la scheda vecchia.
  • La cartella dati del core non si sposta nei profili 1.x (storage.ts dataDirOf, apps/desktop/internal/vaultdir/dbpath_js.go): nel browser i database del core non sono file ma voci del pool SQLite (opfs-sahpool), salvate sotto il path con cui il core le ha aperte (il proprio app.db, lo stato di sync di ogni mount sotto <cartella dati>/mounts/, index.db e sync.db di un vault), e il pool non può rinominare una voce né copiarla in modo atomico. Spostare la cartella avrebbe avviato il core dove nessuna di quelle voci si trova, perdendo lo stato di sync dei mount e le modifiche non caricate. Un profilo che ha già la cartella dati della 1.x continua a usarla (LEGACY_DATA_DIR, avvio del core sul path che ha); un profilo nuovo usa /clarae/data. Allo stesso modo il database di un vault che esiste sotto la cartella di configurazione vecchia tiene quella chiave. Sono path interni, che nessuno vede.
  • Copie delle versioni fino alla 1.3 (cartelle fs e memobrain-sqlite alla radice di OPFS, marker senza il suffisso dell'account, una registrazione del dispositivo per server): all'avvio del workbench un account le adotta (adoptLegacyCopies, registrata in legacy-owner.json alla radice di OPFS, senza spostare file) solo se si dimostra che sono tutte sue: la sessione del core in fs/memobrain/data/auth.json ha lo stesso server e lo stesso utente di GET /me, la registrazione del dispositivo (se c'è) è dello stesso utente, e ogni vault in fs/vaults e ogni mount in fs/memobrain/data/mounts è uno che l'account raggiunge nel cloud (GET /vaults?include_deleted=true, GET /shares?scope=received, letta per intero pagina dopo pagina). Non si adotta in un account che ha già il suo spazio. Altrimenti le copie non si aprono mai, per nessuno: la pagina Account offre di cancellarle, avvisando che possono essere di un altro account e contenere modifiche mai caricate. La vecchia registrazione del dispositivo resta a disposizione finché il suo utente non la riprende (il core la usa solo se è dello stesso utente).
  • Copie private (guard.ts, markers.ts, overlay.ts): i marker in localStorage (clarae.workbench.vaults@<chiave dell'account>) registrano per ogni copia nome, tipo, cartella, pending, conflicts e dirty. Il blocco del vault privato (manuale o per inattività, un solo timer: quello del core) cancella la copia in chiaro se non ci sono modifiche non caricate, altrimenti un overlay bloccante chiede cosa fare. Una copia conservata va sbloccata prima che il workbench la mostri (unlock gate).

Creazione di un vault privato (create.ts, runCreation):

  1. La pagina crea la cartella /vaults/new-<uuid> con un marker privato: se la scheda si chiude durante la creazione, lo sweep successivo cancella la copia vuota.
  2. Apre la cartella e monta la procedura guidata del workbench (mountCreateCloudVault): passphrase due volte (almeno 12 caratteri), SyncAPI.LinkNew, chiave di recupero mostrata una volta.
  3. A creazione riuscita il marker passa all'id cloud (con localPath sulla cartella new-…) e l'indirizzo diventa /vaults/<cloudId>/open (history.replaceState). Il lancio prosegue come un'apertura normale. Le aperture successive trovano la copia nella cartella registrata dal marker (folderOf).
  4. Annullando, la cartella e il marker si cancellano e si torna a /vaults.

Header di sicurezza ​

web-embed aggiunge a ogni risposta: Content-Security-Policy (una delle due sotto), X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY, Cross-Origin-Opener-Policy: same-origin, Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), serial=(), bluetooth=(). HSTS non è impostato dall'app perché il TLS termina all'ingress.

CSP della console (CSP() in services/cloud/web-embed/webembed.go; <issuer-origin> è l'origine dell'issuer OIDC, omessa se l'issuer non è un URL):

text
default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' data:; connect-src 'self' <issuer-origin>; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'

'wasm-unsafe-eval' serve solo a compilare WebAssembly (Argon2id di hash-wasm nell'export dei vault privati); eval e codice inline restano vietati. Nessuno stile inline: la barra della quota usa <progress>, il build non emette <style> né style=.

CSP del workbench (WorkbenchCSP()), servita solo con workbench.html:

text
default-src 'self'; script-src 'self' 'wasm-unsafe-eval' 'sha256-<import-map>'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' blob: <issuer-origin>; media-src 'self' blob:; worker-src 'self' blob:; frame-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'

È la politica di rilascio del desktop più ciò che serve per raggiungere API e issuer:

  • style-src 'unsafe-inline' perché CodeMirror, KaTeX ed Excalidraw calcolano gli stili; gli script inline restano vietati;
  • 'sha256-<import-map>' ammette un solo script inline: l'import map che fissa con SRI i chunk del workbench (vedi sotto). web-embed ne calcola l'hash all'avvio dal workbench.html incorporato (ImportMapHashes); nessun altro script inline passa;
  • worker-src 'self' blob: perché new Worker() non accetta integrity: la pagina scarica lo script di ogni worker (core, layout del grafo, pdf.js) con SRI e lo avvia da un URL blob: dei byte verificati (VerifiedWorker in bridge.ts, sri.ts);
  • img-src/media-src con blob: e data: per le risorse del vault, connect-src blob: per download e risorse del vault.

Nessuna delle due politiche ammette risorse di altre origini (D-01, V-02).

Supporto del campo integrity dell'import map: Chromium 127+ e Firefox 138+ (Safari non verificato). I browser che non lo supportano lo ignorano (caricano i chunk senza verifica, come prima); worker, Excalidraw e WASM sono verificati in ogni browser perché usano fetch con integrity o l'attributo del tag.

I test Go TestBuiltIndexPinsEverySubresourceWithSRI e TestBuiltWorkbenchPinsEverySubresourceWithSRI controllano le pagine incorporate (per il workbench anche l'import map e il suo hash nella CSP servita); TestEveryEmbeddedScriptIsPinned verifica che ogni .js/.mjs della build sia raggiungibile da una catena di SRI che parte dalle pagine (tag → import map → hash incorporati nei chunk). Senza la build vengono saltati; con CLARAE_REQUIRE_WEB_BUILD=1 sono obbligatori. Nel browser, e2e-security/workbench-csp.spec.ts e excalidraw-offline.spec.ts provano che un chunk, il worker del core, il worker di pdf.js ed excalidraw.js alterati non vengono eseguiti.

Cache, compressione e budget ​

  • Cache-Control: i file sotto assets/ e core/ hanno public, max-age=31536000, immutable (in produzione hanno tutti l'hash nel nome, compreso il worker del layout del grafo). Tutto il resto, comprese le pagine e il fallback SPA, ha no-cache.
  • ETag forte per ogni file (SHA-256 calcolato alla prima richiesta), con un valore diverso per ogni rappresentazione (-gz, -id): le rivalidazioni rispondono 304.
  • gzip: i file di testo (.html, .js, .mjs, .css, .svg, .json, .webmanifest, .map, .txt, .xml, .wasm, .ttf, .otf) da 512 byte in su sono compressi una volta, alla prima richiesta. La copia resta in memoria solo se risparmia almeno il 10% e si serve ai client che accettano gzip (Vary: Accept-Encoding).
  • WebAssembly: la build conserva solo core/<nome>-<hash>.wasm.gz (il core è circa 32 MB non compresso). Una richiesta di <nome>.wasm riceve il .gz così com'è se il client accetta gzip; altrimenti lo riceve decompresso in streaming, senza bufferizzarlo, con Content-Length letto dal trailer gzip e senza supporto ai range.
  • Placeholder: dist/ è ignorato da git tranne services/cloud/web-embed/dist/index.html, così go build funziona senza costruire la SPA (la pagina mostra solo un avviso). Dopo task web-build il placeholder risulta modificato: non va committato (task web-clean lo ripristina).

Budget (BUDGET e checkBudget in web/scripts/esbuild.mjs, ADR-0020): la build di produzione fallisce se un limite è superato.

Il core pesava circa 8090 kB con gzip -9 (39,2 MB non compresso, 1° novembre 2026), a meno del 2% dal limite. Il client gRPC delle notifiche non può funzionare nel browser (niente TCP) e nel core WebAssembly non è più compilato (notify_grpc.go con //go:build !js; il core usa solo SSE): con gRPC escono anche protobuf, golang.org/x/net/trace e html/template. Dopo la modifica il core pesava circa 6750 kB gzip (30,7 MB non compresso). In M12 la politica della passphrase è passata nel core (zxcvbn in Go, ADR-0045 §8) e il core ha perso i moduli solo desktop (login OIDC nel browser di sistema, portachiavi, updater, cestino di sistema): il 3 novembre 2026 pesa circa 7030 kB gzip (32,4 MB non compresso), circa il 14% sotto il limite. Dettagli e misure in ADR-0020.

Comandi ​

sh
task dev-web          # dev server esbuild su :5174 con live reload, proxy /api -> :18081
task web-build        # task wasm-core, task wailsjs (solo se mancano i binding), build di produzione, copia in services/cloud/web-embed/dist
task build-cloud      # binario del cloud con la build incorporata (dopo web-build)
task web-clean        # rimuove la build incorporata e ripristina il placeholder tracciato
task e2e-web          # Playwright sulla console con l'API simulata (dev server :5175, CLARAE_E2E=1)
yarn workspace @clarae/web run test             # Vitest + Testing Library
yarn workspace @clarae/web run e2e:workbench-ui # spec del desktop sul workbench web (:5176), prima task wasm-core
yarn workspace @clarae/web run e2e:security     # CSP/SRI sulla build di produzione, prima task web-build
yarn workspace @clarae/web run e2e:cloud        # contro un cloud vero su :18081 (vedi sotto)

task web-build esegue sempre task wasm-core, quindi serve la toolchain Go. Senza il core, la build di yarn workspace @clarae/web run build lo segnala e la pagina del workbench dice che il motore manca.

Sviluppo con login reale: task stack-up, poi task dev-cloud, che avvia anche la Web UI su :5174 (WEB=0 per saltarla, log in .dev/logs/web.log). In alternativa yarn dev:cloud:k3d (--no-web per saltarla; la Web UI si ferma con down/delete). task dev-web serve solo ad avviare la Web UI da sola. Aprire http://localhost:5174 (utenti user1/user2/admin, password clarae-dev-password). Per provare il binario con la SPA incorporata: task web-build build-cloud, poi http://localhost:18081.
