  • Client desktop (apps/desktop): app Wails v3, una finestra principale per processo, più, solo per il terminale integrato (M23, ADR-0064, in implementazione e non rilasciato), una seconda finestra (/terminal.html) che l'utente può aprire e chiudere: le sessioni (shell su pseudo-terminali, apps/desktop/internal/terminal) stanno nel core Go e sopravvivono allo sgancio e al riaggancio, la finestra le disegna soltanto. Il terminale è solo desktop (nel workbench web è un'eccezione di parità), non ha un flag del Config Profile e non si apre nei vault in sola lettura. La UI è il pacchetto condiviso @clarae/workbench (React; editor Live su Milkdown, editor Sorgente su CodeMirror 6, ADR-0049); la logica è il core Go in apps/desktop/internal (vault, indice, link, sync, crittografia), esposto alla UI come binding (App.Services()). Funziona offline su un vault che è una cartella di file ordinari, apribile anche da altri editor. Le applicazioni (pagine web registrate nel vault come file .webapp, ADR-0056) si aprono su macOS, Windows (WebView2) e Linux (WebKitGTK, build GTK3) in una vista nativa del sistema aggiunta come figlia della stessa finestra (ADR-0062 per Windows e Linux, accettato il 2026-11-20, non provati su una finestra reale), dietro il flag features.web_viewer (acceso di default per ADR-0060; un profilo può spegnerlo; fino alla 1.7.1 era spento); dove manca il runtime o con CLARAE_WEBVIEW=off (Windows e Linux), e nel workbench web, si aprono nel browser di sistema.
  • Workbench web: la stessa UI e lo stesso core Go, compilato in WebAssembly (apps/desktop/cmd/clarae-core) e avviato in un Web Worker dalla pagina /vaults/:id/open della Web UI. I file stanno in OPFS e gli indici in sqlite-wasm. Il browser è un dispositivo come gli altri (ADR-0029, ADR-0030).
  • Console web (web/): area utente e amministrazione, in React. Parla con la REST attraverso il client TypeScript generato (@clarae/api-client). La console e il workbench sono compilati e incorporati nel binario del cloud (services/cloud/web-embed, go:embed).
  • Cloud Service (services/cloud): un unico binario Go, modular monolith, con --role=api|worker|all. Il ruolo api serve la REST (/api/v1), il gRPC NotifyService (clarae.v1, e fino alla 2.0 anche il servizio con il package della 1.x, servito dallo stesso handler) e il fallback SSE (GET /api/v1/events); il ruolo worker esegue i job (GC dei blob, upload scaduti, retention, compattazione, purge, riconciliazione delle quote, snapshot, export ZIP). Usa PostgreSQL, uno storage S3-compatibile e Keycloak, rispetto al quale è solo resource server: valida i JWT (JWKS, iss, aud=clarae-api) e controlla lo stato dell'utente nel proprio database. I gruppi esistono solo nel database del cloud (D-05).
  • Notifiche: un commit fa pg_notify; ogni processo ha una sola connessione LISTEN e inoltra gli eventi (vault_changed, config_changed, share_changed, account_changed) agli stream gRPC e SSE dei client. Il client reagisce con un pull.

Sincronizzazione ​

Il merge è sempre sul client: il server ordina e conserva, non interpreta mai il contenuto. Per questo il protocollo è identico per vault privati e condivisi (Specifications.md §3.4, ADR-0009).

  1. Pull: GET /vaults/{id}/changes?since=<cursore>&since_id=<id> restituisce il changelog del vault, ordinato da un seq monotono. Il cursore è una posizione (next_seq) più l'identità del cambiamento a quella posizione (next_id, oppure as_of_id dell'albero): dopo un ripristino del database a un punto precedente i nuovi commit riusano numeri di sequenza già visti, e solo l'identità li distingue (ADR-0046). Un cursore che il server non può proseguire riceve 410 CURSOR_EXPIRED e il client riparte dall'albero del vault (bootstrap): con compaction_seq il cursore è più vecchio della finestra del changelog e l'albero è autorevole; con last_seq il server è tornato indietro e il bootstrap reconcile-upload ripubblica le revisioni e i file che il server ha perso invece di sovrascriverli o cestinarli. Prima di riscrivere un file durante un bootstrap il client ne salva una versione in File recovery.
  2. Risoluzione sul client: il core applica le modifiche remote; se un file ha anche modifiche locali fa il merge a tre vie per .md e per id per i JSON di canvas ed Excalidraw e per la libreria di forme dei disegni (shared/go/merge; la libreria ha una strategia propria, library-by-id, ADR-0054). Lo stesso codice serve l'editor dei disegni aperto, che fonde le modifiche non salvate con una versione nuova del file (VaultAPI.MergeEdit). Gli altri tipi producono una copia di conflitto (D-04). I candidati al merge e i path non decifrabili sono persistiti in sync.db (pending_remote, quarantine, ADR-0039), così un crash o un blocco del vault non perdono nulla.
  3. Push: POST /vaults/{id}/blobs:check dice quali blob (content-addressed, SHA-256) mancano; si caricano con PUT /vaults/{id}/blobs/{sha256} fino a 32 MB, oltre con tus (POST /vaults/{id}/uploads, PATCH /uploads/{id}).
  4. Commit: POST /vaults/{id}/commit con ops[]; ogni operazione porta la base_rev (concorrenza ottimistica) e ha un esito proprio: accepted, conflict (con la revisione corrente, da fondere) o rejected con un codice (BLOB_MISSING, QUOTA_EXCEEDED, ...). Le revisioni sono immutabili (rev_no); nessuna versione viene persa in silenzio, le scartate restano nello storico.

Rename di cartelle (§3.4.7, ADR-0040): su un vault condiviso il motore riconosce una cartella rinominata (dalla UI con Renamed, o dalla scansione: tutti i file che il server ha sotto la cartella spostati allo stesso posto sotto il nuovo nome, e la vecchia cartella sparita dal disco) e la invia come una sola move_prefix, che sposta i file in una transazione e porta con sé le condivisioni; sui vault privati restano le move per file, ciascuna col path cifrato di nuovo. Un SHARE_ROOT_MOVE (l'ultimo file di una cartella condivisa spostato da solo) diventa la move_prefix della radice della condivisione quando il file ha mantenuto il suo posto sotto il nuovo nome; altrimenti lo spostamento resta locale, fermo, e lo stato della sync lo spiega. In arrivo, una serie di move che rinomina un'intera cartella locale si applica con un solo rename della directory e una transazione su sync.db (apps/desktop/internal/sync/folders.go).

La retention dello storico e la compattazione del changelog sono legate (ADR-0038): quando la retention cancella un'operazione strutturale (create, move, delete, restore), compaction_seq avanza, e un client rimasto indietro fa il bootstrap invece di ricevere un changelog con dei buchi. La quota conta solo i file correnti (D-03).

Vault privati e condivisi (D-02, D-06) ​

  • Privato: cifrato end-to-end sul client (shared/go/vaultcrypto, con vettori di test condivisi con packages/vaultcrypto-web). La VMK da 256 bit è avvolta dalla passphrase (Argon2id) e dalla recovery key; il server vede solo blob e path opachi. Non è condivisibile (VAULT_ENCRYPTED); persi passphrase e recovery key, i dati non si recuperano. Le etichette di dominio della cifratura non seguono il nome del prodotto e non cambiano mai (cambiarle renderebbe illeggibili i vault privati esistenti: ADR-0052). Dettagli: security/crypto-design.md.
  • Condiviso: non cifrato lato client, condivisibile con utenti e gruppi; una condivisione ricevuta appare come un mount, cioè un vault separato.
  • La scelta è immutabile (VAULT_KIND_IMMUTABLE). Ogni funzione è per vault (D-06): nessun link, backlink, grafo, ricerca, segnalibro o template attraversa due vault.

Contratti ​

  • REST: api/openapi.yaml è la fonte unica. task gen-openapi genera gli stub del server (oapi-codegen, strict server e validatore delle richieste, services/cloud/internal/api/api.gen.go), il client Go (shared/go/apiclient, usato da apps/desktop/internal/sync/transport) e il client TypeScript (packages/api-client). Gli errori sono application/problem+json con un code allineato a shared/go/syncproto; ogni operazione autenticata dichiara anche i rifiuti dell'autenticazione (401, 403 USER_SUSPENDED, 409 INVALID_STATE per il conflitto d'identità di ADR-0041, 429). tus e SSE sono fuori dal generatore e documentati nell'estensione x-clarae-external-routes (ADR-0037 §3).
  • Config Profile: api/config-profile.schema.json → costanti e default dei flag in Go (shared/go/features) e TypeScript (@clarae/api-client/features), task gen-features.
  • Notifiche gRPC: api/proto/clarae/v1/notify.proto → shared/go/notifyv1 (buf).
  • Database del cloud: query per modulo in services/cloud/internal/db/queries/<modulo>.sql → internal/<modulo>/<modulo>db (sqlc); migrazioni SQL versionate in internal/db/migrations.
  • Binding Wails: i metodi dei servizi Go → packages/workbench/wailsjs (generati, non versionati) e, da questi, il client tipizzato dell'host del browser web/src/workbench/core.gen.ts (versionato). I binding di gestione cloud ricevono e restituiscono i tipi dell'OpenAPI (apps/desktop/internal/app/cloudapi, ADR-0045 §6), quindi i modelli generati da Wails coincidono con gli schemi di @clarae/api-client.
  • Eventi Go → TypeScript: il registro apps/desktop/internal/app/events_registry.go → packages/workbench/src/app/events.gen.ts (nomi e payload, task gen-events). Regole e controlli: desktop-web-sync.md (ADR-0045 §5).
  • Capability e funzioni: le capability dell'host le dichiara il core (apps/desktop/internal/app/capabilities.go) → packages/workbench/src/platform/capabilities.gen.ts e shared/parity/capabilities.gen.json, e dallo stesso generatore i nomi delle cartelle del vault (shared/go/pathrules) → packages/workbench/src/platform/vaultPaths.gen.ts (task gen-capabilities); il registro shared/parity/features.yaml → il tipo FeatureId e le costanti Go shared/go/parity (task gen-parity-features).
  • Verifiche: contract test del client contro il server reale (apps/desktop/internal/sync/transport/contract_test.go), fixture di conformance Go/TS per Markdown, merge e crittografia (shared/conformance), registro di parità (shared/parity/features.yaml, con le prove per superficie di ADR-0045), le suite dei pannelli cloud sul core WebAssembly contro un cloud finto validato sull'OpenAPI (task test-core). Conformance, test-core, registro e codice generato (task check-gen) girano in task ci (ADR-0036); il contract test ha il tag integration e gira con le altre suite lente in task test-desktop-e2e, da eseguire quando si toccano il client della sync o le API.

Parità tra desktop, workbench web e console ​

La parità è per costruzione (ADR-0045): una sola UI (@clarae/workbench) montata da entrambi gli host, una sola logica (App.Services(), servita da Wails sul desktop e dal dispatcher RPC del core WebAssembly nel browser) e un solo modulo per la gestione dei vault cloud (@clarae/cloud-features, dietro CloudPort con un adattatore REST per la console e uno sui binding per desktop e workbench). Le differenze ammesse passano da punti dichiarati e controllati:

  • il confine Host nel core Go, implementato da entrambi gli host e classificato per capability (TestHostCapabilities);
  • le capability, dichiarate dal core e generate per la UI; comandi e azioni dei pannelli le nominano in requires/excludes e dichiarano la loro funzione (FeatureId);
  • eventi e client dell'host generati, e regole ESLint contro nomi di binding e di eventi scritti a mano e controlli sulla piattaforma fuori da platform/;
  • il registro delle funzioni con le prove per superficie: un yes del workbench vuole un test sul core WebAssembly (task parity).

Guida per gli sviluppatori e procedura per una funzione nuova: desktop-web-sync.md; stato misurato: web-workbench-parity.md.

Presenza in tempo reale ​

I vault condivisi hanno un canale WebSocket, GET /api/v1/presence (ADR-0065): avatar e cursori degli altri utenti sullo stesso file. Non è co-editing: il merge resta sul client. La stanza è (vault cloud, file_id); il server timbra l'identità, autorizza per file al join e ricontrolla (condivisioni, sospensione, flag, ogni 60 s). Lo stato è solo in memoria nella replica; tra repliche passa da PostgreSQL LISTEN/NOTIFY (canale presence), senza persistenza, audit né log per frame. Il client è codice Go condiviso, nel core desktop e nel core WebAssembly. Vedi desktop-web-sync.md e la guida dell'amministratore.

Il cloud come modular monolith ​

Ogni modulo è un pacchetto services/cloud/internal/<modulo> con interfacce esplicite. Un modulo dipende solo da db, storage, audit, notify e dalle interfacce degli altri moduli, mai dalle loro tabelle: le sue query generate stanno in <modulo>db, che solo lui importa (depguard), e gli altri passano dalle funzioni esportate (exported.go, con un db.DBTX). La mappa delle tabelle e le eccezioni ammesse sono verificate da internal/db/ownership_test.go (ADR-0033).

Osservabilità ​

  • Metriche Prometheus: il ruolo api espone /metrics sullo stesso listener, servito solo a chiamate dirette: una richiesta inoltrata da un proxy o dall'ingress riceve 404. Il ruolo worker non ha un listener API: le metriche dei job, /healthz e /readyz stanno su un listener interno dedicato (METRICS_LISTEN_ADDR, default 127.0.0.1:18083); il readyz del worker richiede che lo scheduler batta.
  • Probe: /api/v1/healthz (vivo) e /api/v1/readyz (PostgreSQL, S3, Keycloak); i controlli delle dipendenze sono in cache per 2 s e il dettaglio dei controlli va solo ai chiamanti diretti interni (agli altri «ok» o «non disponibile», il resto nel log).
  • Log JSON con request id (X-Request-Id, ripreso nei problem), allarmi e dashboard in deploy/observability. Guida: admin-guide/monitoraggio.md.
