Segreti e variabili della pipeline di rilascio ​

Cosa usa oggi release.yml ​

Dalla 1.2.2 release.yml non legge nessun segreto né variabile del repository: costruisce e pubblica senza firmare (vedi README.md). Usa solo il GITHUB_TOKEN che GitHub crea per ogni run, con permessi minimi per job:

JobPermessi del GITHUB_TOKENUso
image (immagine cloud)contents: read, packages: writelogin e push su GHCR (ghcr.io/<owner>/clarae-cloud)
chart (chart Helm)contents: read, packages: writehelm registry login e push OCI su oci://ghcr.io/<owner>/charts
desktop (installer)contents: read (default del file)nessun accesso in scrittura; gli installer sono artefatti del run
release (GitHub Release)contents: writegh release create con installer e SHA256SUMS

Non serve configurare nulla in Settings, Secrets and variables, Actions. I pacchetti GHCR creati al primo push sono privati: renderli pubblici (Package settings, Change visibility) o concedere l'accesso dalle impostazioni del pacchetto; il chart (.../charts/clarae) è un pacchetto separato. Nessuna chiave o certificato è nel repository e nessuna è stata generata qui.

Da riattivare ​

Il resto di questo documento descrive la pipeline firmata di ADR-0023 e il canale non firmato di ADR-0031, com'erano fino alla 1.2.1. La 1.2.2 ha tolto da release.yml i passi di firma (Apple, Authenticode), notarizzazione, cosign, SBOM, attestazioni e manifest di aggiornamento: impostare oggi questi segreti non ha alcun effetto. Per riattivarli bisogna ripristinare quei passi nel workflow (l'ultima versione completa è quella precedente al commit 4631447) e poi configurare i segreti sotto. Il riferimento resta utile per quel lavoro.

Variabili (pubbliche, tab Variables) ​

NomeUso
UPDATE_PUBLIC_KEYChiave pubblica ed25519 (base64) che i client usano per verificare il manifest di aggiornamento; compilata nel binario con ldflags. Senza di essa l'updater è disattivato nella build: build-desktop.sh --release non compila mai con la chiave di sviluppo.
UPDATE_BASE_URLURL pubblico del canale di aggiornamento (contiene stable/manifest.json e beta/manifest.json, con i .sig). Serve solo con l'updater attivo.
REQUIRE_SIGNING(opzionale) true: un tag senza tutti i segreti di firma fallisce. Default: canale non firmato.
RELEASE_AUTO_PUBLISH(opzionale) true: la release è pubblicata subito. Default: bozza, che una persona promuove dopo la checklist su tre sistemi.
ENABLE_ATTESTATIONS(opzionale) true: pubblica le attestazioni di provenienza GitHub (immagine e file della release). Servono un repository pubblico o un piano che le includa: su un repository privato senza piano il passo fallisce ("Feature not available"). Cosign firma comunque l'immagine.
LINUX_ARM64_RUNNER(opzionale) etichetta di un runner arm64, es. ubuntu-24.04-arm (gratuito nei repository pubblici). Senza, nessun installer Linux arm64.
WINDOWS_TIMESTAMP_URL(opzionale) server RFC 3161, default http://timestamp.digicert.com.

Segreti (tab Secrets) ​

Manifest di aggiornamento (opzionale: senza, niente aggiornamenti automatici) ​

NomeContenuto
UPDATE_SIGNING_KEYChiave privata ed25519, base64 (64 byte o seed da 32). Generazione: vedi "Generare la chiave" sotto. Custodire anche una copia offline cifrata.

macOS (firma e notarizzazione) ​

NomeContenuto
APPLE_CERT_P12_BASE64Certificato Developer ID Application con chiave privata, esportato in .p12, in base64.
APPLE_CERT_PASSWORDPassword del .p12.
APPLE_SIGNING_IDENTITYNome dell'identità, es. Developer ID Application: Nome Cognome (TEAMID).
APPLE_API_KEY_P8_BASE64Chiave API App Store Connect (AuthKey_XXXX.p8) in base64, per notarytool.
APPLE_API_KEY_ID, APPLE_API_ISSUERKey ID e Issuer ID della chiave API.

Alternativa locale a APPLE_API_*: NOTARY_KEYCHAIN_PROFILE (profilo di xcrun notarytool store-credentials) oppure APPLE_ID + APPLE_APP_PASSWORD + APPLE_TEAM_ID (scripts/release/package-macos.sh accetta tutte e tre le forme).

Windows (Authenticode) ​

NomeContenuto
WINDOWS_CERT_PFX_BASE64Certificato di code signing (OV/EV) con chiave privata in .pfx, base64.
WINDOWS_CERT_PASSWORDPassword del .pfx.

Un certificato EV su token hardware non è utilizzabile da un runner ospitato da GitHub: serve un runner self-hosted o un servizio di firma in cloud (in quel caso definire direttamente CLARAE_SIGNTOOL_CMD, vedi build/windows/installer/project.nsi).

Immagini OCI e chart Helm ​

Nessun segreto aggiuntivo: la firma cosign era keyless (identità OIDC del workflow, permesso id-token: write, oggi non concesso) e il push su GHCR usa GITHUB_TOKEN (packages: write), come oggi.

Generare la chiave del manifest ​

Su una macchina fidata, offline (il tool stampa solo su stdout, non scrive file):

sh
task release-tool
bin/release gen-key      # private -> segreto UPDATE_SIGNING_KEY, public -> variabile UPDATE_PUBLIC_KEY

Salvare la chiave privata in un password manager o in un HSM/vault e tenerne una copia offline cifrata. Per ricavare la pubblica da una privata esistente: CLARAE_UPDATE_SIGNING_KEY=... bin/release pubkey. Prima di impostare i segreti verificare la coppia: bin/release gen-manifest ... && bin/release sign-manifest -in manifest.json && bin/release verify-manifest -in manifest.json -pubkey <pubblica>.

Chiave di sviluppo ​

Senza UPDATE_PUBLIC_KEY una build locale si fida della chiave di sviluppo, derivata da una frase pubblica (internal/updater/key.go): chiunque può firmare manifest accettati da quei binari. Va bene per test locali, mai per build distribuite: per questo --release fallisce, a meno di ALLOW_UNSIGNED_UPDATES=1 (la pipeline lo imposta quando mancano le chiavi), che compila l'updater fuori dal binario.
